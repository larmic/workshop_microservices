Hausaufgabe erledigt?

Ihr bringt einen Mini-Service in eurer Sprache mit: GET /health antwortet mit 200, ein Dockerfile baut das Image, der Container lauscht auf Port 8080. Den Workshop-Stack habt ihr einmal mit make docker-up-hub gestartet.

Zur Vorbereitung → Noch nicht fertig? Jetzt nachholen, oder setzt euch zu jemandem, bei dem es läuft.

  1. Einklinken

    • In services/.env den Pfad zu eurem Service eintragen: CUSTOM_BOOKING_PATH=/absoluter/pfad/zu/eurem/service
    • Stack neu starten: Ctrl+C, dann make docker-up-hub. Compose baut euren Service als booking-custom mit.
    • Die Backend-URLs (FLIGHT_SERVICE_URL, HOTEL_SERVICE_URL, CAR_SERVICE_URL, CONSUL_URL) bekommt euer Container automatisch. Nicht selbst setzen.

  2. Testen

    Mein Service: wird geprüft …

    curl -i http://localhost:8099/health                # direkt: HTTP/1.1 200
curl -i http://localhost/api/booking-custom/health  # über das Gateway: 200
docker logs booking-custom                          # eure Logs, nicht Kotlin/Ktor

    Achtung: Ohne eigenen Pfad läuft hier die mitgelieferte Beispiel-Lösung (Kotlin/Ktor). Dann ist auch alles grün. Erst die Logs zeigen, ob es wirklich euer Service ist.

  3. Weiterarbeiten

    Ab jetzt erweitert ihr genau diesen Service. Nach einer Code-Änderung nur ihn neu bauen, in einem zweiten Terminal im Ordner services/:

    docker compose -f docker-compose.yml -f docker-compose.infra.yml \
  -f docker-compose.reference.yml -f docker-compose.custom.yml \
  up -d --build booking-custom

    In jeder Story schaltet ihr oben zwischen Referenz und Mein Service um. Details: docs/custom-setup.md

Aufgabe User Story + Akzeptanzkriterien

Kontext

Der erste Booking-Service: läuft auf dem Entwicklerrechner, in der Cloud, auf einem Raspberry Pi — überall gleich. Mit Health-Check (damit Probleme früh auffallen) und externer Konfiguration (damit ein Build in jeder Umgebung läuft).

User Story

Als Betriebsteam möchte ich einen Service, der in beliebigen Umgebungen ohne Code-Änderung läuft und sich automatisch überwachen lässt, damit Probleme früh erkannt werden und Deployment-Pfade nicht spezifisch sein müssen.

Akzeptanzkriterien

  • GET /health liefert 200 wenn der Service gesund ist
  • Logs auf stdout
  • Backend-URLs (Flight/Hotel/Car) konfigurierbar über Umgebungsvariablen
  • GET /info zeigt die aktuelle Konfiguration
  • GET /openapi liefert die OpenAPI-Spec aus — Vorlage: booking/story1/api/openapi.yaml
  • Dockerfile im Service-Verzeichnis baut ein lauffähiges Image (Service lauscht auf Port 8080)
  • Pfad zum Service in services/.env als CUSTOM_BOOKING_PATH eingetragen, sodass make docker-up-hub den Service mitbaut
  • GET /booking/offers aggregiert Flight, Hotel und Car und liefert kombinierte Ergebnisse
Spickzettel 3 Schritte · Pseudo-Code

  1. Konfiguration aus der Umgebung

    Backend-URLs als Umgebungsvariablen lesen, nichts im Code verdrahten.

    FLIGHT_SERVICE_URL=http://flight:8080
HOTEL_SERVICE_URL=http://hotel:8080
CAR_SERVICE_URL=http://car:8080

  2. Health, Info und OpenAPI

    Drei kleine Endpunkte, damit Plattform und Menschen sehen, was läuft.

    GET /health  → 200 OK
GET /info    → { config: { flightServiceUrl, hotelServiceUrl, carServiceUrl } }
GET /openapi → OpenAPI-Spec (text/yaml)

  3. Angebote aggregieren

    Drei Aufrufe nacheinander, das Ergebnis zusammenbauen. Fehler dürfen durchschlagen, kein Error-Handling.

    GET /booking/offers
  → GET FLIGHT_SERVICE_URL/flights
  → GET HOTEL_SERVICE_URL/hotels
  → GET CAR_SERVICE_URL/cars
  → { flights, hotels, cars }

                    Aufgabe User Story + Aufgabe
                    

                        
Diese Story findet am Flipchart statt. Es gibt keine Referenz-Implementierung, keinen Service und keinen Port. Das Dashboard zeigt hier nur die Aufgabe.

                        
Kontext

                        
Der Booking-Service liefert Angebote. Als Nächstes wird gebucht, und wo gebucht wird, wird storniert und umgebucht. Bevor jemand losprogrammiert, entsteht die API am Flipchart: Ressourcen statt Verben, Idempotenz macht Retries sicher, Status-Codes sind Infrastruktur.

                        
User Story

                        
Als Produktverantwortliche möchte ich eine API für Storno und Umbuchung, die HTTP so nutzt, wie es gemeint ist, damit Retries sicher sind, Fehler sichtbar werden und wir sie nicht in drei Monaten umbauen.

                        
Aufgabe

                        
    
                            
  • Teams zu 3 bis 4 Personen, ein Flipchart pro Team, ca. 20 Minuten
    • 
                            
  • Szenario: eine Kundin storniert die ganze Reise (Grund soll nachvollziehbar bleiben), ein Kunde bucht nur den Flug um
    • 
                            
  • Randbedingung: der Client wiederholt Anfragen bei Timeout
    • 
                        

                        
Ergebnisformat

                        
Eine Tabelle, eine Zeile pro Endpoint:

                        
    
                            
  • Methode und Pfad
    • 
                            
  • Request-Kern, Antwort und Status-Code
    • 
                            
  • idempotent ja/nein
    • 
                            
  • Begründung, auch für bewusste Abweichungen
    • 
                        

                        
Danach: je Team zwei Minuten Vorstellung, dann Quiz im Plenum. Die Regeln nehmt ihr mit in Story 3, dort entsteht POST /booking/bookings.                     Aufgabe User Story + Akzeptanzkriterien
                    

                        
Kontext

                        
Statische URLs sind eine schöne Idee für Folien, aber nicht für den Betrieb. Backend-Services registrieren sich bei Consul; der Booking-Service findet sie über logische Namen statt fest verdrahteter Adressen. Läuft eine zweite Instanz, übernimmt sie, sobald sich die erste abmeldet oder ihr Health-Check fehlschlägt.

                        
User Story

                        
Als Betriebsteam möchte ich Backend-Services über logische Namen finden, statt URLs per Hand zu pflegen, damit Skalierung und Ausfälle ohne nächtliche Config-Edits funktionieren.

                        
Akzeptanzkriterien

                        
    
                            
  • Resolver fragt GET /v1/health/service/{name}?passing=true bei Consul
    • 
                            
  • Statische URLs ersetzt durch logische Namen: flight-service, hotel-service, car-service
    • 
                            
  • Bestehender GET /booking/offers aus Story 1 umgebaut, löst Flight/Hotel/Car über den Consul-Resolver auf statt über statische Env-URLs
    • 
                            
  • POST /booking/bookings orchestriert die drei Backend-Services und antwortet mit 201 Created und der aggregierten Buchung
    • 
                            
  • Aus Story 2 mitgenommen: Ressource bookings statt Verb, POST antwortet mit 201 Created, Fehler kommen als Status-Code, nicht als 200 mit Fehler-Body
    • 
                            
  • Optional: Client-Side Load Balancing bei mehreren Instanzen (zufällige Auswahl)
    • 
                        

                    

                

                

                    Spickzettel 3 Schritte · Pseudo-Code
                    

                        
    
                            
  1. 
                                
    Instanz bei Consul finden
    
                                
    Nur gesunde Instanzen abfragen und eine davon zufällig wählen.
    

    resolve(name):
  res = GET consul:8500/v1/health/service/{name}?passing=true
  // res = [ {Service:{Address, Port}}, ... ]
  instance = randomPick(res)
  return "http://{instance.Address}:{instance.Port}"
    
                            
    2. 
                            
  2. 
                                
    Angebote über den Resolver
    
                                
    Der Endpunkt aus Story 1, nur ohne feste URLs.
    

    GET /booking/offers:
  for svc in [flight-service, hotel-service, car-service]:
    url = resolve(svc)
    results[svc] = GET url/...
    
                            
    3. 
                            
  3. 
                                
    Buchung orchestrieren
    
                                
    Neu: eine Buchung über alle drei Services, die API aus Story 2.
    

    POST /booking/bookings { flightId, hotelId, carId, customerName }:
  for svc in [flight-service, hotel-service, car-service]:
    url = resolve(svc)
    POST url/bookings
  → { bookingId, customerName, flight, hotel, car }

                    Aufgabe User Story + Rollenspiel
                    

                        
Diese Story wird gespielt, nicht programmiert. Ihr seid die Suchanfragen, Booking hat den Schalter. Das Circuit-Breaker-Panel darunter zeigt anschließend die Referenz-Implementierung.

                        
Kontext

                        
Der Flight-Service ist zeitweise nicht erreichbar (Netzprobleme, Überlast, Deployment). Ohne Schutz wartet der Booking-Service bei jeder Anfrage drei Sekunden auf den Timeout und reißt seine Aufrufer mit. Ein Circuit Breaker zählt die Fehler, schaltet nach fünf Fehlern in Folge ab, antwortet sofort mit einem Fallback und probiert nach einer Pause vorsichtig wieder zu.

                        
User Story

                        
Als Kundin möchte ich Hotel und Mietwagen auch dann sehen und vergleichen können, wenn die Flugsuche ausfällt, damit ich nicht vor einer hängenden Seite sitze.

                        
Rollen

                        
    
                            
  1. Booking hat Strichliste, Schild CLOSED / OPEN / HALF_OPEN und Karten „Hotel ✓ · Car ✓ · flights: []". Warten heißt laut zählen: eins, zwei, drei, Timeout.
    2. 
                            
  2. Flight folgt den geheimen Ansagen des Trainers. Hotel und Car antworten sofort.
    3. 
                            
  3. Alle anderen sind Suchanfragen auf GET /booking/offers. Wer eine Antwort hat, legt die Karte in den Korb und stellt sich sofort hinten wieder an.
    4. 
                        

                        
Ablauf

                        
    
                            
  1. Runde 1, ohne Schalter: Flight schweigt. Nach drei Sekunden sagt Booking „500" und fragt Hotel und Car gar nicht erst.
    2. 
                            
  2. Runde 2, mit Schalter: Bei jedem Timeout macht Booking einen Strich, fragt Hotel und Car und gibt die Karte „Hotel ✓ · Car ✓ · flights: []". Nach fünf Strichen in Folge ruft Booking „OPEN". Ab dann fragt Booking Flight nicht mehr: Karte sofort, dazu „Circuit open!".
    3. 
                            
  3. HALF_OPEN: 30 Sekunden nach „OPEN" ist der nächste Gast die Probe und bekommt das PROBE-Token, nur er darf zu Flight. Wer dahinter steht, bekommt sofort die Karte. Bleibt Flight still: OPEN, die 30 Sekunden laufen neu. Antwortet Flight: Liste wegwischen, CLOSED.
    4. 
                            
  4. Runde 3a, wackliges Flight: Flight antwortet jedes zweite Mal. Jede Antwort wischt die Liste weg.
    5. 
                            
  5. Runde 3b, rote Gäste: Flight ist gesund, aber fünf Anfragen haben ein kaputtes Datum. Flight sagt sofort „400".
    6. 
                        

                        
Und die Buchung?

                        
Lesen und Schreiben sind zwei Fälle. Was passiert, wenn der Flight-Breaker offen ist und jemand auf Buchen klickt, besprechen wir nach dem Recap, und in Story 6 noch einmal.

                        
Vollständige Beschreibung mit Material zum Nachbauen: docs/stories/story-04-circuit-breaker.md. Referenz-Implementierung: services/booking/story4/.

                    

                

            

        

            
Circuit-Breaker-Demo (Referenz Story 4)

            

                

                    
                    

                        
                        

                    

                

            

            

        


        


        
        

            

                

                    Aufgabe User Story + Rollenspiel
                    

                        
Diese Story wird gespielt, nicht programmiert. Gleiche Schlange, gleiches Schild wie Story 4. Neu: Takt, Chips und ein langsames Hotel. Kein geheimes Briefing. Das Bulkhead-Panel darunter zeigt anschließend die Referenz-Implementierung.

                        
Kontext

                        
Antwortet der Hotel-Service extrem langsam, binden seine Aufrufe die Ressourcen des Booking-Service, in einem klassischen Server den gemeinsamen Thread- oder Connection-Pool. Dann warten auch Anfragen an den Flight-Service, obwohl dieser einwandfrei funktioniert, bis sie beim Aufrufer in den Timeout laufen. Das Bulkhead-Pattern gibt jedem Backend einen eigenen Pool: Läuft einer voll, bleiben die anderen trocken. Der Code dafür ist trivial, die Größe des Pools nicht.

                        
User Story

                        
Als Betriebsteam möchte ich, dass Probleme mit einem Backend-Service nicht die Aufrufe an andere Backend-Services beeinträchtigen, damit ein langsamer oder fehlerhafter Service nicht das gesamte System blockiert.

                        
Material

                        
Sechs Chips, ein Bulkhead-Tablett (drei Spalten Flight / Hotel / Car mit je zwei Mulden, zwei steckbare Trennwände; alternativ ein großer Becher, dann drei Becher), ein A4-Blatt als Uhr mit den Feldern 1 bis 8, Suchkarten 1 bis 20, 20 Karten hotels: [], Schild und Strichliste aus Story 4. Spielbar ab sieben Personen. Nach jeder Runde Stapel und Uhr zurücksetzen. Druckvorlagen: Materialseite.

                        
Rollen

                        
    
                            
  1. Takt zählt laut 1 bis 8, immer wieder, und klatscht, sobald Booking und Hotel „fertig" sagen. Pro Klatscher nimmt die vorderste Suchanfrage die nächste Suchkarte vom Stapel (1 bis 20), gibt sie Booking und stellt sich sofort hinten wieder an. Stapel leer: Runde vorbei.
    2. 
                            
  2. Booking ruft Flight, Hotel und Car nacheinander, jeder Aufruf braucht einen Chip. Wartende Karten liegen in einer Reihe bei Booking. Fertige Suchen auf zwei Stapel: komplett und hotels: []. Timeout zwölf Takte ab Hotel-Aufruf, dann Strich wie in Story 4.
    3. 
                            
  3. Hotel legt Karte und Chip auf das Feld der Uhr (A4, Felder 1 bis 8), das Takt gerade gerufen hat. Kommt die Zahl wieder, gibt Hotel zuerst beides zurück, dann kommt die neue Karte. Flight + Car tippen den Chip nur an.
    4. 
                            
  4. Alle anderen sind Suchanfragen.
    5. 
                        

                        
Ablauf

                        
    
                            
  1. Probelauf: Tablett ohne Wände, sechs Chips, Hotel gibt schon beim nächsten Takt zurück. Drei Takte.
    2. 
                            
  2. Runde 1, ohne Wände, ein Pool mit sechs Chips: Eine Karte von Hotel behält ihren Chip für Car, erst danach geht er an die älteste wartende Karte. Wie viele Karten liegen nach 20 Takten ohne Chip in der Reihe?
    3. 
                            
  3. Runde 2, mit Wänden, je zwei Chips für Flight / Hotel / Car: Hotel-Spalte leer? Sofort hotels: [], weiter zu Car. Wie viele der 20 Suchen bekommen einen Hotel-Chip?
    4. 
                            
  4. Nach Runde 2: Steht das Schild noch auf CLOSED?
    5. 
                        

                        

                            Was passieren sollte erst nach der Vorhersage
                            

                                
    
                                    
  • Runde 1: vier, ab Suche 7 wartet jede schon auf Flight.
    • 
                                    
  • Runde 2: sechs, die anderen 14 sofort.
    • 
                                    
  • Nach Runde 2: ja, acht Takte liegen unter zwölf, und Rejects erreichen den Breaker nie.
    • 
                                

                            

                        

                        
Warum ausgerechnet zehn? (ca. 15 Minuten)

                        
Little’s Law: L = λ × W. L sind die gleichzeitig laufenden Aufrufe, also die benötigten Slots, λ die Aufrufe pro Sekunde, W die Dauer eines Aufrufs. Der Booking-Service schickt 20 Hotel-Aufrufe pro Sekunde. Hotel antwortet in 50 ms, 500 ms oder erst nach dem 3-Sekunden-Timeout. Legt euch vorher fest: Braucht ein langsames Backend mehr, weniger oder gleich viele Slots?

                        

                            Die Rechnung erst nach der Vorhersage
                            

                                
50 ms ergeben 1 Slot, 500 ms ergeben 10, ein 3-Sekunden-Timeout ergibt 60. Zehnmal langsamer heißt zehnmal mehr Slots, bei gleichem Verkehr. Dimensioniert wird aber auf die normale Latenz: Ist der Pool voll, weil das Backend degradiert, ist das das Signal. Im Spiel: normal L = 1 Chip, langsam L = 8, Pool 2.

                    Aufgabe User Story + Akzeptanzkriterien
                    

                        
Kontext

                        
Eine Reise = Flug + Hotel + Mietwagen. Schlägt die Hotelbuchung fehl, nachdem der Flug schon gebucht wurde, muss der Flug storniert werden. DB-Transaktionen funktionieren nicht über Service-Grenzen — das Saga-Pattern ersetzt die fehlende Transaktion durch Kompensationsschritte. Atomar ist das nicht.

                        
User Story

                        
Als Kunde möchte ich eine Komplettbuchung (Flug + Hotel + Mietwagen) durchführen, die am Ende entweder vollständig steht oder nichts mehr gebucht ist, damit ich nicht mit einer unvollständigen Buchung dastehe.

                        
Akzeptanzkriterien

                        
    
                            
  • Orchestrierte Saga: Flight → Hotel → Car (zentraler Koordinator)
    • 
                            
  • Jeder Service bietet einen Stornieren-/Kompensieren-Endpoint (DELETE /bookings/{id})
    • 
                            
  • Bei Fehler in einem Schritt: alle vorherigen Schritte kompensieren (Rollback in umgekehrter Reihenfolge)
    • 
                            
  • Status pro Saga abfragbar: PENDING, COMPLETED, COMPENSATING, FAILED
    • 
                            
  • Optional: Retry-Logik für Kompensation; Timeout-Handling; Persistenz für Recovery
    • 
                        

                    

                

                

                    Spickzettel 3 Schritte · Pseudo-Code
                    

                        
    
                            
  1. 
                                
    Saga anlegen
    
                                
    Status und Schritte festhalten, gebuchte IDs für den Rückweg merken.
    

    saga = { id, status: PENDING, steps: [] }
booked = []                          // für Rollback
    
                            
    2. 
                            
  2. 
                                
    Vorwärts buchen
    
                                
    Schritt für Schritt, jeder erfolgreiche Schritt landet in booked.
    

    try:
  flight = POST flight/bookings { ... }
  booked.push({ svc: "flight", id: flight.id })
  saga.steps.push({ svc: "flight", status: BOOKED })

  hotel = POST hotel/bookings { ... }
  booked.push({ svc: "hotel", id: hotel.id })
  saga.steps.push({ svc: "hotel", status: BOOKED })

  car = POST car/bookings { ... }
  saga.steps.push({ svc: "car", status: BOOKED })

  saga.status = COMPLETED
    
                            
    3. 
                            
  3. 
                                
    Rückwärts kompensieren
    
                                
    Schlägt ein Schritt fehl, werden die gebuchten in umgekehrter Reihenfolge storniert.
    

    catch error at step X:
  saga.status   = COMPENSATING
  saga.failedAt = X
  for b in reverse(booked):
    DELETE b.svc/bookings/{b.id}     // Kompensation
    mark step COMPENSATED
  saga.status = FAILED
    
                            
    4.

                    Aufgabe User Story + Rollenspiel
                    

                        
Diese Story wird gespielt, nicht programmiert. Ihr seid die Kund:innen. Car sagt immer nein. Der Becher zeigt, was wirklich storniert wurde. Das Saga-Panel darunter zeigt anschließend die Referenz-Implementierung.

                        
Kontext

                        
In Story 6 trägt der Booking-Service die volle Verantwortung für die Kompensation: Er ruft synchron DELETE /bookings/{id} gegen jeden Backend-Service auf und behandelt jeden Fehler selbst. Fachlich ist die Stornierung aber Aufgabe der Backends. Booking ruft ihnen das Storno deshalb nur noch als Event zu und wartet nur, bis es angenommen ist. Ehrlich gesagt ist das ein Mittelweg: Booking dirigiert den Hinweg, storniert wird per Zuruf.

                        
User Story

                        
Als System möchte ich bei einer fehlgeschlagenen Buchung die Kompensation asynchron an die zuständigen Backend-Services delegieren, damit der Booking-Service nicht für deren Verfügbarkeit haften muss und die Backends ihre eigene Stornierungslogik kapseln können.

                        
Material

                        
Pro Tisch: sechs verdeckte Listen (je drei für Hotel und Flight), ein Becher pro Reise, etwa sieben Gummibärchen pro Reise (Alternative: Büroklammern), ein Korb, pro Reise zwei nummerierte Zettel, eine Strichliste, ein Briefing-Kärtchen für Flight. Ab 12 Personen zwei Tische.

                        
Rollen

                        
    
                            
  1. Booking hat eine Strichliste und bucht eine Reise nach der anderen bei Flight, Hotel und Car. Sagt Car nein, storniert Booking rückwärts, erst Hotel, dann Flight. Danach sagt Booking „storniert“.
    2. 
                            
  2. Hotel und Flight buchen auf einer verdeckten Liste. Stornieren heißt: an den Fingern bis fünf zählen, durchstreichen, ein Gummibärchen in den Becher der Reise. Jedes Mal, auch wenn die Reise schon durchgestrichen ist. Flight folgt den geheimen Ansagen des Trainers.
    3. 
                            
  3. Car hat heute keine Autos und sagt immer „nein“. In Runde 3 ist Car auch der Korb.
    4. 
                            
  4. Alle anderen haben je eine Reise. Die Becher stehen nummeriert auf dem Tisch, angestellt wird nach Reisenummer. Die nächste Reise kommt dran, wenn die vorige „storniert“ gehört hat. Storniert niemand mehr und ist der Korb leer: Kassensturz, in jeden Becher gehören zwei.
    5. 
                        

                        
Ablauf

                        
    
                            
  1. Runde 1, Anruf (wie Story 6): „Hotel, storniere Reise 1!“ Booking wartet auf „erledigt“, dann dasselbe mit Flight. Wer wartet?
    2. 
                            
  2. Runde 2, Zuruf (unsere Referenz): Das Backend ruft sofort „gehört!“ und storniert danach, Booking ruft gleich das nächste Backend. Bleibt es still, zählt Booking laut bis drei, macht einen Strich und meldet trotzdem „storniert“. Stimmt jeder Becher?
    3. 
                            
  3. Runde 3, Korb: Booking wirft pro Storno einen Zettel in den Korb und meldet sofort „storniert“. Der Korb liest die Zettel der Reihe nach vor, das Backend storniert und sagt „quittiert“. Fehlt das nach dem Gummibärchen, zählt der Korb laut bis fünf und liest denselben Zettel noch einmal. Stimmt jeder Becher?
    4. 
                        

                        

                            Was passieren sollte erst nach dem Kassensturz
                            

                                
    
                                    
  • Runde 1: die ganze Schlange, aber Booking weiß alles.
    • 
                                    
  • Runde 2: nein, und Booking hat es sogar gemerkt.
    • 
                                    
  • Runde 3: keiner fehlt, einer hat drei.
    • 
                                

                                
Danach: Die Leiter

                                
Booking storniert nicht mehr selbst, antwortet aber weiter der Kund:in. Was fehlt, damit jeder Becher stimmt und Booking es weiß?

                                
    
                                    
  • Zuruf: Booking wartet nur auf „gehört“. Ist Flight weg, ist das Storno weg. Webhook, unsere Referenz.
    • 
                                    
  • Korb: Der Korb hält den Zettel fest und liest vor, bis quittiert wird. Keiner fehlt, manches kommt doppelt. Broker, at-least-once.
    • 
                                    
  • Nummer: Wer sich die Zettelnummer merkt und sie wiedererkennt, quittiert nur, ohne Gummibärchen. eventId, Idempotenz.
    • 
                                    
  • Antwortzettel: Booking meldet „storniert“ erst, wenn beide Antworten da sind. Sonst zählt Booking bis zehn und meldet STUCK. Reply, Timeout.
    • 
                                

                                
Eventing macht das Problem nicht kleiner. Es macht es leiser.

                    Aufgabe User Story + Akzeptanzkriterien
                    

                        
Kontext

                        

                            Die Service-Logs zeigen jede Anfrage isoliert: Booking loggt seine Saga, Flight/Hotel/Car loggen
                            ihre lokalen Buchungen — aber niemand kann ein POST /booking/bookings über
                            alle Services hinweg als eine zusammenhängende Operation verfolgen. Korrelation
                            passiert heute nur über Timestamps und Augenmaß. Mit jeder zusätzlichen Komponente wird das
                            schmerzhafter, spätestens bei eurer Saga aus Story 6 (bis zu fünf HTTP-Calls über drei
                            Backends: drei Forward, zwei DELETE).
                        

                        

                            Eine Trace-ID pro eingehender Anfrage, die durch alle nachgelagerten Aufrufe
                            propagiert wird, löst das Problem — auch ohne eigenes Tracing-Backend: ein
                            grep <trace-id> über die Compose-Logs zeigt den kompletten Ablauf.
                        

                        
User Story

                        

                            Als Entwickler:in im Betrieb möchte ich
                            einen einzelnen Geschäftsvorgang über Service-Grenzen hinweg in den Logs verfolgen können,
                            damit ich Fehlerursachen, Latenzen und Saga-Verläufe gezielt analysieren kann, ohne Logs
                            nach Zeitstempeln zusammenzupuzzeln.
                        

                        
Akzeptanzkriterien

                        
Ausgangspunkt ist euer Booking-Service aus Story 6: Saga Flight → Hotel → Car,
                            Kompensation per DELETE /bookings/{id}. Events, Circuit Breaker oder Bulkhead
                            braucht ihr nicht.

                        
    
                            
  • Bei jedem eingehenden Request am Booking-Service wird ein Trace-Kontext erzeugt oder aus dem
                                Header übernommen (W3C Trace Context: traceparent).
    • 
                            
  • Die Response trägt den effektiven traceparent zurück. Das Panel unten liest die
                                Trace-ID daraus.
    • 
                            
  • Der Trace-Kontext wird auf jedem ausgehenden HTTP-Call weitergereicht: Forward
                                (POST /bookings) und Kompensation (DELETE /bookings/{id}).
    • 
                            
  • Jede Logzeile eures Booking-Service enthält die Trace-ID. Flight, Hotel und Car übernehmen
                                einen eintreffenden traceparent schon und loggen ihn.
    • 
                            
  • Logs sind strukturiert (JSON), damit trace_id ein eigenes Feld ist.
    • 
                            
  • Der Filter aus dem Panel zeigt den vollständigen Ablauf einer Buchung, Forward
                                und Kompensation. Eine Kompensation löst ihr mit „Buchung mit kaputtem
                                Mietwagen“ aus.
    • 
                            
  • Die OpenAPI-Dokumentation des Booking-Services beschreibt den
                                traceparent-Header.
    • 
                        

                        
Story 6 nicht fertig? Die Kriterien gelten für die Calls, die ihr habt,
                            mindestens einer. Die Kompensation zeigt der Trainer an der Referenz.

                        
Bonus: Detektiv-Runde unten im Panel, oder die Kompensation als Event wie in der
                            Story-7-Referenz (Spickzettel).

  1. 
                                
    Header übernehmen oder erzeugen
    
                                
    Server-Middleware: eingehenden traceparent lesen, sonst neu erzeugen, und in der Response zurückgeben.
    

    // W3C: 00-<trace-id-32hex>-<span-id-16hex>-<flags-2hex>
on incomingRequest(req):
  tc = parse(req.header("traceparent")) ?: generateNew()
  res.header("traceparent") = tc.toHeader()    // zurück zum Client
  ctx = ctx.with(tc)
  next(req.withContext(ctx))
    
                            
    2. 
                            
  2. 
                                
    Header weitergeben
    
                                
    Pro ausgehendem Aufruf eine neue Span-ID, die Trace-ID bleibt gleich.
    

    on outgoingRequest(ctx, req):
  tc = ctx.get(TraceContext)
  hop = tc.copy(spanId = randomSpanId())
  req.setHeader("traceparent", hop.toHeader())
    
                            
    3. 
                            
  3. 
                                
    Auch bei der Kompensation
    
                                
    Das DELETE ist ein ganz normaler ausgehender Aufruf.
    

    compensate(ctx, step):
  outgoingRequest(ctx, DELETE step.url + "/bookings/" + step.bookingId)

  4. 
                                
    trace_id in jede Logzeile
    
                                
    Strukturiert loggen, damit der Filter die Zeilen findet.
    

    log.info("forward step done",
  trace_id: ctx.tc.traceId, span_id: ctx.tc.spanId, step: "flight")

publish(event)

Distributed Tracing (Booking Story 8)

            

            
Nach jedem Call zeigt die Anzeige unten die trace_id aus dem traceparent-Response-Header und liefert einen kopierbaren Filter-Befehl. Damit lässt sich der komplette Vorgang über alle vier Services hinweg in den Compose-Logs rekonstruieren.
